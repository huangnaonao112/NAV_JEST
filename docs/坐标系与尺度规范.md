# 坐标系与尺度规范

> 适用模块：`src/models/*`、`resources/qml/*`、`src/RackStatusClient.cpp`
>
> 唯一事实来源：**`src/models/CoordinateSystem.h`**
>
> 最后更新：2026-11-03（对应提交：修复"整屏绿块 / 月面轨迹不可见"）

---

## 0. 一句话结论

> 本项目**不是**"所有东西用一个比例"，而是**三套坐标空间**：
> 天体局部（1 单位 = 1 km）、地月压缩（1 单位 ≈ 4.805 km）、报文原始单位。
>
> 永久避免尺度错乱的办法不是"统一成一个数字"，而是：
> **每个空间只允许一个命名常量，跨空间必须显式转换，QML 禁止写字面量（有 ctest 强制）。**

---

## 1. 三套坐标空间

### 1.1 空间 A：天体局部空间（Body-Local Space）

| 属性 | 值 |
|---|---|
| 比例 | **1 场景单位 = 1 km** |
| 依据 | Qt Quick 3D 内置图元 `#Sphere` 的基准半径是 **50**（直径 100），节点 `scale` 直接乘在半径上 |
| 地球 | 半径 6371 km → `scale = 6371 / 50 = 127.42` → 场景半径 6371 单位 |
| 月球 | 半径 1737 km → `scale = 1737 / 50 = 34.74` → 场景半径 1737 单位 |
| 大气辉光 | 6421 km → `scale = 128.42` |
| 使用对象 | 地球/月球本体、卫星轨道环、地面标记点、月面轨迹、卫星模型 |

**关键规则**：
- 轨道环的点坐标 = 半长轴 `a`（km），**直接**喂给几何体，不再乘任何系数；
- `TrajectoryLineGeometry.thickness` 与 `GroundWarningItem.radius` 的单位
  **必须与点坐标一致**（同属空间 A 时就是 km）。

### 1.2 空间 B：地月压缩空间（Earth-Moon Display Space）

| 属性 | 值 |
|---|---|
| 比例 | **1 场景单位 ≈ 4.805 km**（= 384400 / 80000） |
| 压缩比 | `DISTANCE_SCALE = 80000 / 384400 ≈ 0.2081` |
| 月球摆位 | `x = 80000` 单位 |
| 使用对象 | `$TRJ` 回放轨迹、`TrajectoryLoader` 读入的 ECI/ECEF 轨迹、月球整体位置 |

**为什么需要压缩**：真实地月距离 384400 km。若按 1:1 摆放，月球在 384400 单位外，
地心视角（相机距离 30000）下完全看不到。压缩到 80000 单位后地月可同屏，
这是**有意的展示取舍**，不是物理错误。

**注意**：只有"月球的位置"被压缩，"月球的大小"仍是空间 A 的真实比例
（半径 1737 单位）。这是非物理的混搭，但视觉上可接受；新增跨空间物体时必须
意识到这一点。

### 1.3 空间 C：报文原始单位（Telemetry Space）

| 报文 | 字段含义 | 进入哪个空间 |
|---|---|---|
| `$TRJ` | ECEF/ECI 三轴 **km** | × `DISTANCE_SCALE` → 空间 B |
| `$MNT` | 月面**经纬度(deg)** + 高度(km) | `llaToCartesian` → 空间 A（月球局部） |
| `$PNT` | 经纬度(deg) + 高度(m) | 经纬度无比例问题 |
| `$SAT` | 星下点经纬度(deg) | 同上 |
| `$JAM` | 经纬度(deg) + 半径(km) | 经纬度直接转空间 A |

## 2. 常量清单（唯一来源）

全部定义在 `CoordinateSystem`（QML 侧同一类型可直接用 `CoordinateSystem.xxx`）。

### 2.1 物理参数

| 常量 | 值 | 说明 |
|---|---|---|
| `SPHERE_PRIMITIVE_RADIUS` | 50.0 | Qt `#Sphere` 基准半径（**所有 scale 推导的基石**） |
| `EARTH_RADIUS` | 6371.0 | km |
| `MOON_RADIUS` | 1737.4 | km（真实平均） |
| `MOON_RADIUS_DISPLAY` | 1737.0 | km（显示用整数，对应 scale 34.74） |
| `EARTH_MOON_DISTANCE_REAL` | 384400.0 | km |
| `MOON_SCENE_X` | 80000.0 | 空间 B 中月球 X 位置 |

### 2.2 节点缩放

| 常量 | 推导 | 值 |
|---|---|---|
| `EARTH_NODE_SCALE` | 6371 / 50 | 127.42 |
| `MOON_NODE_SCALE` | 1737 / 50 | 34.74 |
| `ATMOSPHERE_NODE_SCALE` | 6421 / 50 | 128.42 |
| `DISTANCE_SCALE` | 80000 / 384400 | ≈0.2081 |

### 2.3 标记与线宽

| 常量 | 值 | 单位 | 用途 |
|---|---|---|---|
| `GROUND_MARKER_ALTITUDE` | 6391.0 | km | 地球表面标记抬升 |
| `MOON_TRAIL_RADIUS` | 1740.0 | km | 月面轨迹点半径（略高于月面） |
| `ORBIT_THICKNESS_KM` | 40.0 | km | 轨道环线宽（默认相机下约 2 px） |
| `DECEPTION_ORBIT_THICKNESS_KM` | 70.0 | km | 欺骗卫星轨道环线宽 |
| `REPLAY_THICKNESS_UNITS` | 80.0 | 空间 B 单位 | `$TRJ` 回放轨迹线宽 |
| `MOON_TRAIL_THICKNESS_KM` | 30.0 | km | 月面轨迹线宽（约 1~2 px） |

> **判据**：线宽 / 轨迹包围盒对角线 ∈ [1e-4, 0.5]。
> 可用 `CoordinateSystem::thicknessIsPlausible(extent, thickness)` 自检；
> `TrajectoryLineGeometry` 在 rebuild 时会自动告警一次。

## 3. 开发规则（必须遵守）

### 3.1 写代码时

1. **QML 禁止尺度字面量**
   ```qml
   // ❌ 禁止
   scale: Qt.vector3d(127.42, 127.42, 127.42)
   thickness: 30.0
   x: 80000

   // ✅ 正确
   scale: Qt.vector3d(CoordinateSystem.earthNodeScale, ...)
   thickness: CoordinateSystem.moonTrailThicknessKm
   x: CoordinateSystem.moonSceneX
   ```

2. **C++ 禁止另建常量**
   ```cpp
   // ❌ 禁止
   constexpr double MOON_SCENE_X = 80000.0;
   constexpr double KM_TO_SCENE = 0.01;

   // ✅ 正确
   constexpr double MOON_SCENE_X = CoordinateSystem::MOON_SCENE_X;
   ```

3. **跨空间必须显式转换**，不要"顺手乘个系数"：
   ```cpp
   CoordinateSystem::toDisplaySpace(realKm);   // 空间 C(km) → 空间 B
   CoordinateSystem::toRealKm(displayUnits);   // 空间 B → km
   ```

4. **点坐标与线宽/半径同空间**：几何体的 `thickness` 必须与 `points` 同单位。

### 3.2 新增一个渲染物时（检查清单）

- [ ] 它的点坐标属于哪个空间？在注释里写明（`空间 A` / `空间 B`）
- [ ] 节点 `scale` 由 `CoordinateSystem` 推导，而不是手写
- [ ] `thickness` / `radius` 与点坐标同单位，取自常量
- [ ] 跨空间时调用显式转换函数
- [ ] `ctest -R qml_unit_lint` 通过
- [ ] 默认相机（距离 30000，fov 35°）下目视确认可见且不过粗
- [ ] 在本文档第 5 节"新增记录"里补一行

### 3.3 单位命名约定

| 后缀 | 含义 | 例子 |
|---|---|---|
| `...Km` | 千米（空间 A 或真实物理） | `moonTrailThicknessKm` |
| `...Units` | 场景单位（空间 B） | `replayThicknessUnits` |
| `...Scale` | 节点缩放（乘在 `#Sphere` 半径 50 上） | `earthNodeScale` |

## 5. 事故复盘

### 2026-11 整屏绿块 / 月面轨迹不可见

**现象**：勾选"低轨"后整个 3D 视口变成纯绿 `#00C853`；月面红色轨迹线永远看不见。

**根因 1（渲染）**：`TrajectoryLineGeometry::appendSegmentVertices` 每段写 36 个
`float`，却返回 12（顶点数）。`ptr` 是 `float*`，每段只前进 12 个 float，导致：
- 后段覆盖前段 2/3 数据；
- 缓冲区后 2/3 是从未写入的未初始化内存；
- 未初始化字节被当成坐标 → 随机超大三角形 → 整屏色块。

**根因 2（尺度）**：
| 位置 | 错误 | 后果 |
|---|---|---|
| 轨道环 | `thickness = 0.4`（应 40 km） | 细成亚像素，看不见 |
| 月面轨迹 | 点被 `×0.01`，线宽仍传 30 | 轨迹缩进月球内部 / 巨带 |
| 地面标记 | `radius / 100` | 标记小 100 倍，不可见 |

**教训**：
1. 渲染几何的"数量"和"单位"必须分开测试；
2. 尺度只能有一个事实来源，且 QML 不得写字面量；
3. **提交前必须真正编译并运行**——上一轮因源码缺大括号导致编译失败，
   测试的其实是旧 exe，得出"已修复"的错误结论。

## 7. 轨迹渲染方案评估与性能（2026-11-03）

### 7.1 为什么用"交叉双四边形 ribbon"而不是别的

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 交叉双四边形 ribbon**（当前） | 单 draw call；无自定义着色器；任意视角可见；实现简单稳定 | 每段 12 顶点、2× 填充率；线宽随缩放变化 | 采用，配合下方"线宽自适应" |
| B. `#Cube` 逐段拼接（旧实现） | 实现直观 | 每段一个 Model（千级节点/draw call）；跳点采样；接缝明显 | 已淘汰 |
| C. 线段图元（`Lines` 拓扑） | 顶点最少 | 线宽只能是 1px，且 Qt 各后端支持不一致 | 已淘汰 |
| D. 自定义材质做屏幕空间扩宽 | 顶点最省（8/段）、线宽恒定像素 | 需写 vertex shader + 方向属性，跨平台风险高 | 备选，当前收益不足 |
| E. 实例化线段 | GPU 端每段一次实例 | Qt Quick 3D 实例表维护复杂 | 备选 |

**结论**：A 是 Qt Quick 3D 在不写自定义着色器时的工程最优解；D/E 只有在需要"亚像素宽度控制 + 百万级线段"时才值得投入。

### 7.2 线宽自适应（解决 A 的固有缺陷）

世界单位线宽的问题：视距 30000 时 40 km 约 2px，放大到 1400 时同一条线变成 6px 粗带。
处理：**按 `cameraDistance / DEFAULT_CAMERA_DISTANCE` 等比缩放线宽**（上限 4×、下限 0.15×），
等效于"屏幕恒定宽度"，无需着色器：

```qml
readonly property real lineWidthScale: Math.max(0.15, Math.min(4.0,
    cameraDistance / CoordinateSystem.defaultCameraDistance))
thickness: CoordinateSystem.orbitThicknessKm * lineWidthScale
```

实测：近距离（1400）线宽由 6px 降到约 1.5px，默认视角外观不变。

### 7.3 数据通路（性能的关键，不是几何体）

| 指标（10000 点上限，持续追加） | 优化前 | 优化后 |
|---|---|---|
| 帧率 | 162–166 fps | **180 fps（vsync 上限）** |
| 单帧最大卡顿 | **64 ms** | **7–9 ms** |
| 几何体重建 | 0.63 ms/次 | 0.63 ms/次（非瓶颈） |
| QML 每帧对象分配 | 3N 次跨语言调用 + N 个 `Qt.vector3d` | **0** |

瓶颈原本在 QML 侧：`for (i<count) { trajectory3DX(i); trajectory3DY(i); trajectory3DZ(i) }`
对每个点做 3 次跨语言调用并创建 JS 对象，10k 点、30 次/秒 → 100 万次调用/秒 + GC 压力。

改造：
1. `PntDataModel::trajectory3DScenePoints` 一次返回全部场景点（C++ 内完成压缩变换）；
2. 模型侧 33ms 时间窗口合并 `trajectory3DChanged`，无论来点多快，下游最多 30 次/秒；
3. `TrajectoryLineGeometry` 在可见点数未变时跳过重建（points 与 drawCount 连续变化时避免重复构建）。

**新规则：任何实时渲染数据都不要在 QML 里逐点循环。** 模型必须提供批量访问器，
C++ 侧完成坐标换算与节流。

### 7.4 已评估但暂不做的优化

| 优化 | 收益 | 不做的原因 |
|---|---|---|
| 索引缓冲 + 顶点共享（12→8 顶点/段） | 顶点/上传量 −33% | 当前 0.63 ms 构建、180 fps 已达 vsync 上限，无可见收益 |
| 轨迹点抽稀（按距离裁剪） | 长历史时降低顶点数 | 会损失曲线细节，且万点已在预算内 |
| 拐角圆角/接头补片 | 极近距离更顺滑 | 当前缩放范围内接缝 < 0.1px，不可见 |
| 屏幕空间着色器 | 线宽绝对恒定 | 自定义材质跨平台风险高，收益不及实现成本 |

若未来出现"单场景 10 万点"或"移动端 60fps 硬约束"，按 7.4 前两项的顺序再优化。
